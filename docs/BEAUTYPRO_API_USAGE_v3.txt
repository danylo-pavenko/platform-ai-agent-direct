Що робить інтеграція
--------------------------------------------------------------------------------

Direct AI Agents — AI-асистент у Instagram Direct для салонів.
Підключення до BeautyPro дає повний booking flow:

  • sync довідників (locations, categories, positions, services, employees);
  • пошук / створення / оновлення client за phone / email / name;
  • вільні слоти за графіком майстра (free_time);
  • запис, додавання послуги, видалення послуги, скасування, перенесення;
  • історію візитів (history + sales duration для paid).

Запити з нашого сервера після auth/database.
Для кожного салону потрібен Grant access у Marketplace BeautyPro.

Нижче — порядок, у якому ми тестуємо інтеграцію end-to-end.
Кожен крок = реальні endpoints з нашого коду.
Header на всіх data-запитах: Authorization: Bearer {access_token}

--------------------------------------------------------------------------------
Крок 0. Auth
--------------------------------------------------------------------------------

  GET /v1/auth/database
      ?application_id={APP_ID}
      &application_secret={APP_SECRET}
      &database_code={DATABASE_CODE}
  → access_token, refresh_token?, server

  GET /v1/auth/refresh?refresh_token=…
  → новий access_token (TTL access ≈ 24h)

При 401 EXPIRED — refresh, інакше повторний /auth/database.
Auth завжди на api.aihelps.com (server 1). Data — api / api4 за полем server.

Очікуємо: status granted (після Marketplace Grant access).
Якщо pending — далі data-запити не йдуть.

--------------------------------------------------------------------------------
Крок 1. Sync довідників (admin / sync-worker)
--------------------------------------------------------------------------------

  GET /v1/locations
      ?fields=name,city,street,phone,timezone,active
  → філії (active фільтруємо на нашому боці)

  GET /v1/services/categories
      ?fields=name&archive=false

  GET /v1/positions
      ?fields=name&role=professional
  → грейди / посади майстрів

  GET /v1/services
      ?fields=name,description,duration,category,public,location_prices,archive,price_currency
      &public=true&archive=false
  → каталог послуг + ціни по локаціях

  GET /v1/employees
      ?fields=name,archive,public,roles,positions,position_names
      &role=professional&archive=false
  → майстри

Очікуємо: ≥1 active location, послуги з duration, майстри public.

--------------------------------------------------------------------------------
Крок 2. Client (пошук або створення)
--------------------------------------------------------------------------------

  GET /v1/clients
      ?fields=name,firstname,lastname,phone,email,archive
      &archive=false
      &phone={UA phone variants: +380… / 380… / 0XX…}
      ← без comment у fields (live 400 Unknown parameter 'comment')

  (fallback) GET /v1/clients … &email=…
  (fallback) GET /v1/clients … &name=…   ← Instagram filter у API немає;
                                           шукаємо name / comment з IG:@handle

  Якщо немає:
  POST /v1/clients
  body: { firstname, lastname, phone, email? }
  → { id }   ← fields на POST НЕ передаємо; comment у body НЕ передаємо
               (live 400 Unknown parameter)

  Якщо є і треба оновити контакти:
  PUT /v1/clients/{id}
  body: { firstname, lastname, phone, email? }

Очікуємо: client UUID для наступних кроків.

--------------------------------------------------------------------------------
Крок 3. Вільні слоти (get_available_slots)
--------------------------------------------------------------------------------

  GET /v1/employees/free_time
      ?from={day start UTC ISO}
      &to={day end UTC ISO}
      &duration={сума хвилин послуг}
      &step=15m|30m|60m…          ← live відхиляє step=auto
      &location={location_id}
      &services={service_uuid,…}
      &professionals={employee_uuid}   ← опційно, якщо вибрано майстра
      &public_employees=true|false
      &nearest_day_only=false          ← потрібні всі слоти дня
      &add_now_time=20

  Fallback у коді (якщо порожньо / 400):
    1) public_employees=true + services
    2) без public_employees + services
    3) без services filter

  GET /v1/employees
      ?fields=name,archive,public,roles
      &location={location_id}&role=professional&archive=false
  → підписи імен до UUID з free_time

Очікуємо: відкритий день майстра + конкретний HH:MM у відповіді.
Якщо дня немає в free_time — book НЕ робимо (MASTER_DAY_CLOSED /
SLOT_NOT_AVAILABLE), навіть при force=true на appointments.

--------------------------------------------------------------------------------
Крок 4. Новий запис (book_appointment)
--------------------------------------------------------------------------------

  Якщо master_id не передано:
  GET /v1/employees
      ?fields=name,public,archive
      &location={location_id}
      &service={service_uuid,…}
      &role=professional&archive=false
      [&public=true]

  GET /v1/employees/pick_professional
      ?date=YYYY-MM-DD
      &professionals={uuid,uuid,…}
  → professional UUID

  Повторна перевірка графіка:
  GET /v1/employees/free_time  (день відкритий + час у слотах)

  POST /v1/appointments?force=true
  body:
  {
    "date": "YYYY-MM-DD",
    "location": "{location_uuid}",
    "client": "{client_uuid}",
    "state": "planned",
    "comments": "…",                    ← notes візиту (plural)
    "services": [
      {
        "service": "{service_uuid}",
        "professional": "{employee_uuid}",
        "start": "HH:MM:SS",
        "duration": 60
      }
    ]
  }
  → { id }   ← fields=id на POST НЕ передаємо (live 400)

force=true за замовчуванням (перекриття / merge / stale free_time).
force НЕ створює зміну, якщо майстер того дня не працює — це ловимо
на free_time до POST.

Один planned/confirmed appointment на date+location+client — API може
змерджити послуги при повторному POST.

Очікуємо: appointment UUID у відповіді; smsError (якщо є) — non-fatal.

--------------------------------------------------------------------------------
Крок 5. Додати послугу до візиту (повторний book / append)
--------------------------------------------------------------------------------

  PUT /v1/appointments/{id}?force=true
  body:
  {
    "services": [
      {
        "service": "{service_uuid}",
        "professional": "{employee_uuid}",
        "start": "HH:MM:SS",
        "duration": 45,
        "action": "insert"
      }
    ]
  }

Очікуємо: у візиті ≥2 service lines.

--------------------------------------------------------------------------------
Крок 6. Змінити склад — прибрати послугу (remove_appointment_service)
--------------------------------------------------------------------------------

  GET /v1/appointments/{id}
      ?fields=state,services(id,service,serviceName,start,duration,professional)
  → lineId потрібної послуги

  Якщо послуг > 1:
  PUT /v1/appointments/{id}?force=true
  body:
  {
    "services": [
      { "id": "{lineId}", "action": "delete" }
    ]
  }

  Якщо лишилась остання послуга:
  PUT /v1/appointments/{id}
  body: { "state": "cancelled", "cancelReason": "Cancelled via Instagram agent" }

Очікуємо: послуга зникла з візиту АБО весь візит cancelled.

--------------------------------------------------------------------------------
Крок 7. Перенесення (reschedule_appointment)
--------------------------------------------------------------------------------

Окремого move/reschedule endpoint у BeautyPro API немає.
Наш ланцюжок:

  1) PUT /v1/appointments/{old_id}
     body: { "state": "cancelled", "cancelReason": "Cancelled via Instagram agent" }

  2) GET /v1/employees/free_time   ← нова дата / час

  3) POST /v1/appointments?force=true   ← новий візит (як крок 4)
     ті самі services / client / location (або оновлені)

Очікуємо: старий state=cancelled, новий id з новою date/time.

--------------------------------------------------------------------------------
Крок 8. Скасування всього візиту (cancel_appointment)
--------------------------------------------------------------------------------

  PUT /v1/appointments/{id}
  body:
  {
    "state": "cancelled",
    "cancelReason": "Cancelled via Instagram agent"
  }

Prefer cancel (state) over DELETE.
Очікуємо: state=cancelled.

--------------------------------------------------------------------------------
Крок 9. Same-day lookup (merge / TIME_CONFLICT)
--------------------------------------------------------------------------------

  GET /v1/appointments
      ?fields=date,location,client
      &client={id}&location={id}
      &from={day}T00:00:00.000Z&to={day}T23:59:59.999Z
      &state=planned,confirmed

Використовуємо, коли POST без force дав 409 TIME_CONFLICT —
шукаємо вже існуючий візит того ж клієнта на той день.

--------------------------------------------------------------------------------
Крок 10. Історія клієнта (get_client_crm_history)
--------------------------------------------------------------------------------

  GET /v1/clients/{id}/history
      ?fields=date,duration,professional,professional_name,paid,
              items(id,name,type,quantity,sum,sale_id),feedback
  → ~останні 2 місяці (обмеження API); потрібен scope full

  Для paid visits з sale_id:
  GET /v1/sales/{sale_id}
      ?fields=sale_date,duration,calendar_date
  → actual duration (wall-clock до закриття продажу)

Очікуємо: список візитів з items[].name / duration.

    (окремого move endpoint немає)

    GET /clients/{id}/history
    GET /sales/{sale_id}

  sync / admin probe
    GET /locations, /services/categories, /positions, /services, /employees
