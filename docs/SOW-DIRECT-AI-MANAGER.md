**Проєкт:** розробка white-label платформи AI-агента для Instagram Direct  
**Робоча назва продукту:** Direct AI Manager  
**Тип документа:** Statement of Work · фіксований обсяг + опційна фаза масштабування  
**Версія:** 1.0 · листопад 2026  
**Валюта:** USD, без ПДВ (ПДВ — окремим рядком у договорі, якщо застосовно)  
**Мова документа:** українська (юридичні додатки можуть дублюватись англійською)

Цей SOW описує **створення платформи під ключ** з передачею виключних майнових прав на результати робіт Замовнику. Це **не** тариф підписки на вже існуючий SaaS і **не** впровадження одного акаунта Instagram.

У документі немає посилань на продакшен-сайти, репозиторії чи імена кінцевих брендів. Назви постачальників API (Meta, CRM, месенджери, перевізники) наведені лише як **об’єкти інтеграції** в обсязі робіт.

## 2. Мета продукту (коротко)

Direct AI Manager — платформа, у якій:

1. Клієнт бренду пише в **Instagram Direct** офіційним Meta Graph API.  
2. **AI-агент** відповідає в тоні бренду, знає каталог / послуги, збирає замовлення або запис, або кваліфікує лід.  
3. Команда бачить діалоги в **адмінці**, отримує картки в **Telegram**, синхронізує дані з **CRM**.  
4. Кожен бренд — **ізольований тенант** (ОС-користувач, БД, процеси, домен, знання).  
5. **Control plane** (Super Admin) піднімає тенантів, деплоїть, бекапить, бачить health флоту.

Цінність для бізнесу: зняття рутини з менеджерів у Direct, структуровані заявки, запис без «сліпих» слотів, масштабування кількості брендів без змішування даних.

## 5. Обсяг Фази A — що входить

### 5.1. Платформа і тенанти

- Ізоляція: Linux-користувач, PostgreSQL, PM2-процеси (`api` / `bot` / `sync` / `admin`), TLS, окремий домен адмінки.  
- Провіжинінг тенанта з control plane; шифроване сховище секретів; секрети не в логах і не в клієнтських відповідях API.  
- Асинхронний деплой з фіксацією попереднього git SHA; при провалі health — відкат коду (міграції БД — лише forward-compatible).  
- Нічне автооновлення за TZ тенанта (тумблер + спільний секрет).  
- Бекапи (dump + об’єктне сховище), журнал, процедура restore.  
- Health: процеси, авторизація LLM, попередження про сирітські CLI-процеси.  
- Ролі тенанта: owner / manager; Telegram-прив’язка; аудит адмін-дій; експорт даних при offboarding.

### 5.2. Канал Instagram / Meta

- OAuth з мінімальним набором messaging-скоупів для Page-linked IG DM.  
- Hub вебхуків: HMAC, маршрутизація за business id + додатковий routing id; клієнтський sender id не є ключем тенанта.  
- Вхідні DM, вихідні DM, typing, реакції, Stories reply (кадр / still), shared post, розпізнаний телефон, голос (локальний STT), зір для зображень.  
- Echo відповідей менеджера з застосунку Instagram — окремий шлях без LLM; діалог → handoff.  
- Coalesce кількох бульбашок в один хід агента; session freshness; імпорт короткої історії при першому контакті.  
- Public / Debug whitelist для безпечного прогрівання.

### 5.3. Рантайм агента

- Виклик моделі через Agent SDK (гарячий CLI-hotfix окремим прапорцем).  
- Режими: **sales**, **leadgen**, **booking**, **general** (об’єднання інструментів).  
- Системний промпт у БД (версії, активація, відкат); runtime-ін’єкції (час TZ, профіль, каталог/послуги, інструменти).  
- Інструменти: каталог, доставка, ТТН, запис/скасування/перенесення, історія клієнта, handoff, події тенанта, локальне замовлення / бриф.  
- Запобіжники: не світити UUID клієнту; не book з порожнім телефоном; не трактувати підтвердження існуючого візиту як новий запис; prefer CRM-ім’я над Instagram headline.  
- Handoff: одна ескалаційна картка; клієнтський текст — лише за явним прапорцем tool; SLA-нагадування в робочі години.

### 5.4. Інтеграції (Фаза A — обов’язковий набір)

| Інтеграція | Призначення в обсязі |
|---|---|
| **Meta Graph / Instagram Messaging** | канал клієнта |
| **KeyCRM** | каталог, замовлення, ліди, покупець, читання ТТН |
| **CleverBOX** | послуги, філії, слоти, запис |
| **BeautyPro** (і споріднені лінійки API того ж вендора) | послуги, слоти, запис, клієнт, історія; UUID-ідентифікатори |
| **Altegio** | Online Booking v1 (слоти/запис) + B2B v2 (довідники/скасування); один майстер на запис |
| **Нова Пошта** | вартість доставки; трекінг / пошук у кабінеті відправника за правилами приватності |
| **Telegram Bot API** | операційні картки менеджерам (не канал клієнта) |
| **LLM runtime (Claude Agent SDK / CLI)** | генерація відповіді та tool-loop |
| **S3-сумісне сховище** | бекапи тенантів |
| **Whisper (self-hosted)** | транскрипція голосових у DM |

Маршрутизація CRM: `single` | `by_action` | підказка з промпту. HTTP до CRM — лише через адаптер, не з оркестратора діалогу.

**Явно не в Фазі A:** Shopify, Google Sheets як каталог, платіжні шлюзи з checkout-посиланням, створення ТТН, Укрпошта/Meest, Conversions API / GA4, розсилки, Pipedrive/HubSpot/Zoho як CRM ядра, WhatsApp / Viber / Telegram-для-клієнта.

### 5.5. Адмінка тенанта (mobile-first)

Дашборд, діалоги, замовлення, промпти, навчання агента (diff промпту), пісочниця, AI-помічник (метрики + confirm-gated ops), події (календар оферів для агента), синхронізація, CRM-поля, користувачі, налаштування інтеграцій і SLA.

### 5.6. Control plane (Super Admin)

Тенанти, воркери/сервери, деплой-джоби, OAuth hub, журнал вебхуків, бекапи, версія платформи, алерти флоту, базовий трекінг лідів лендинга (без маркетингового кабінету enterprise).

## 7. Критерії приймання (Фаза A)

Приймання — на **двох** ізольованих тестових тенантах (умовні бренди «Retail A» і «Salon B»), без використання даних реальних клієнтів Замовника.

| № | Критерій | Доказ |
|---|---|---|
| A1 | Ізоляція | Запис / діалог тенанта A відсутній у БД і UI тенанта B |
| A2 | Meta DM | Вхід → відповідь агента; менеджерський echo без LLM; Stories reply з кадром |
| A3 | Sales | Пошук каталогу → collect/local order → картка Telegram → дзеркало KeyCRM (якщо write увімкнено) |
| A4 | Booking | Слот з free_time створюється; закритий день / відсутній час — відмова; cancel / reschedule окремими tools |
| A5 | Leadgen | Бриф + Telegram + лід у CRM |
| A6 | Handoff | Одна ескалація; клієнтський custom-текст лише з явним прапорцем |
| A7 | Промпт | Версія → активація → відкат без деплою коду |
| A8 | Control plane | Провіжинінг, деплой з відкатом, бекап, health |
| A9 | Безпека поставки | Немає секретів у логах приймальних сценаріїв; клієнту не світяться внутрішні id |
| A10 | Документація | Runbook експлуатації, матриця інтеграцій, інструкція offboarding |

Маркетинговий орієнтир «відповідь за N секунд» **не є** SLA приймання: хід включає затримку відповіді та холодний старт моделі. Приймається факт відправки після завершення ходу і коректне гасіння typing.

## 11. Управління змінами

1. Будь-яка вимога поза розділами 5 і 8 фіксується Change Request.  
2. CR містить: опис, вплив на строк, години, ціну, ризик регресії.  
3. Робота стартує лише після письмового підтвердження Замовника.  
4. Вирізання майлстоуну з Фізи A не зменшує ціну пропорційно «екранам»: платформа здається як зв’язний контур; часткова відмова від обсягу — переукладення додатку.

---

## 12. Гарантія

- **90 календарних днів** після фінального акта Фази A.  
- Дефекти Blocker / Critical — усунення в пріоритеті без додаткової оплати.  
- Minor / cosmetic — у планових вікнах.  
- Дефект через зміну API постачальника після приймання — оплачувана адаптація (CR), якщо постачальник зламав контракт без backward compatibility і немає обходу в межах початкового обсягу.

---

## 13. Передача результатів

До фінального акта Виконавець передає:

1. Повний вихідний код і історію репозиторію (або архів snapshot + інструкція доступу).  
2. Скрипти провіжинінгу, деплою, бекапу/restore.  
3. Схеми БД і міграції.  
4. Runbook експлуатації флоту і тенанта.  
5. Матрицю інтеграцій і змінні оточення (без продакшен-секретів у відкритому вигляді — через agreed secret handoff).  
6. Акт приймання з переліком пройдених сценаріїв A1–A10.
